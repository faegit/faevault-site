Security Whitepaper

Encryption design & security architecture.

This document details the encryption scheme, key management, threat model, and platform security mechanisms used by FAEVault.

Encryption Architecture

Key Derivation

The master password is derived into a 256-bit key using scrypt(N=2¹⁶, r=8, p=1). scrypt is a memory-hard function widely adopted to resist ASIC/GPU brute-force attacks.

Symmetric Encryption

AES-256-GCM (Galois/Counter Mode) provides both confidentiality and authenticated integrity protection. Each encryption operation uses a unique random Nonce.

File Format

Layout: MAGIC(4B) + VERSION(1B) + SALT(16B) + NONCE(12B) + CIPHERTEXT(with GCM tag). Byte-compatible with the desktop .pmv format for bidirectional exchange.

Key Management

Master Password

The master password is used only for key derivation — never stored or cached. Each unlock requires re-entry or biometric verification via AndroidKeyStore.

Biometrics

Fingerprint/face data protected by AndroidKeyStore with AES/GCM wrapping. Key material is bound to TEE/SE hardware isolation — even the OS cannot extract raw biometrics.

Session Security

Decrypted master key exists only in app process memory and is cleared immediately on lock. FLAG_SECURE hides content from recent task screenshots.

Recovery Phrase

A security question + answer pair derives a recovery key via scrypt, which decrypts a locally stored master password recovery package. No third party involved.

Platform Security

Screen Protection

Global FLAG_SECURE prevents screenshot, screen recording, and screen mirroring. The app requests the highest refresh rate mode on devices locked to 60Hz by FLAG_SECURE.

Clipboard Guard

Sensitive fields marked as is_sensitive (Android 13+ system hides previews). Clipboard auto-clears after 60 seconds.

Brute-force Lockout

After 5 consecutive failed unlock attempts, exponential backoff kicks in: 30s → 60s → 90s → … doubling each time. All attempts are rejected during cooldown.

Sensitive Data Gate

Viewing credit card, ID, or API key details, modifying the master password, or exporting data requires re-entering the current master password.

Autofill Security

Per-action Auth

Every fill or save requires strong biometric or master password authentication. No in-memory plaintext cache is maintained.

Origin Verification

Exact matching by associated app package name or HTTPS host. Requests from the app itself, system settings, or privileged management apps are rejected.

Security Boundaries

No accessibility services, floating windows, auto-start, or battery whitelist permissions. Autofill applies to login entries only.

Sync Security

Transport Encryption

WebDAV connections enforce HTTPS with optional TLS certificate pinning (SHA-256). LAN sync uses SPAKE2P256 zero-knowledge key exchange.

End-to-End

Data remains encrypted (AES-256-GCM) throughout transit — only ciphertext is transmitted. Servers, intermediaries, and cloud providers cannot decrypt content.

Integrity Verification

After sync, ciphertext is read back and decrypted to verify integrity. Logically identical content skips unnecessary remote overwrites.

Threat Model

Local Attacker

Malicious apps on the same device are blocked by FLAG_SECURE and app sandbox isolation. Master password or biometric verification is the only path to vault contents.

Device Loss

The device lock screen is the first defense. The vault file uses scrypt + AES-256-GCM encryption — without the master password, decryption is infeasible. Brute force is throttled by exponential lockout.

Offline Attack

Even if an attacker obtains the .pmv file, they must first crack scrypt before attempting AES decryption. scrypt's memory-hard property makes large-scale parallel attacks prohibitively expensive.
