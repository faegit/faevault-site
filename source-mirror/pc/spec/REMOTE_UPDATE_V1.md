# Remote encrypted-file update reminders v1

Implemented 2026-10-07 for Android and PC. No dedicated server is required: associated SAF/cloud-folder files and WebDAV targets are supported.

The per-target detection toggle is independent of automatic sync and defaults to off. Detection runs every five minutes only in an unlocked live session; Android additionally pauses regular polling when backgrounded, whereas desktop polling continues while minimized. Entering the cloud page and unlocking request a throttled check. The cloud master switch, target association and existing operation/session guards apply. Detection does not modify remote files or download vault contents; WebDAV uses HEAD only with no GET fallback.

An initial successful observation establishes a silent baseline unless a prior successful operation already recorded a confirmed version. Version tokens are opaque equality values (ETag or usable size/modification time), not timestamp ordering. Missing/unsupported metadata cannot invent a new version. Same pending version is deduplicated across restarts; history retains the latest 32 notified tokens per vault/target/association. A changed association resets its baseline. Disabling detection clears pending indication but retains confirmed baseline/history; removing an association clears its context. Errors preserve pending state and are retried without repeated pop-up notifications.

The in-app card reports a changed remote file, target and detection time, with Sync now using the existing validated merge workflow and Later preserving the card without another toast for the same version. A successful operation acknowledges both its authenticated consumed version and its verified resulting/uploaded version, clearing only a matching pending version and preserving a different later observation. Optional acknowledgement metadata failures do not fail an otherwise valid transfer.

Android notifications are generic and private, separated by account/target notification tags and immutable intent identities. Clicking waits for normal unlock if necessary, rejects another vault, and opens the corresponding provider section once. PC's Qt tray API does not identify the originating notification; all clicks safely open the synchronization overview without selecting a target or automatically unlocking. In-app provider cards guide the next user action. Notification permission denial or an unavailable desktop tray does not remove the persistent in-app indication.

System notices contain no passwords, user entry titles or server addresses. State lives in each client's protected configuration, not shared vault entries; deduplication is local per device. Metadata-only detection does not yet identify the device that wrote a change. SAF/sync-folder providers with unchanged/coarse timestamps and identical size can conceal updates; no byte download is performed to compensate.

Tests: shared `remote_update_v1_fixtures.json` covers silent baseline, repeated versions, snooze, stale acknowledgment, merged upload consumed B/result C/new D, own upload, missing metadata and association reset. Controller tests cover HEAD-only requests, startup without opening the page, lock/config/epoch/busy guards, persistent card/no-tray, QObject disposal, overwrite acknowledgments and safe generic navigation. Existing cloud lineage/CAS/scheduler and UI tests were rerun. Native notification delivery and real provider cache behavior require device/provider testing.
